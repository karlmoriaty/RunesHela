## 1. 复核提示（D-02 已定；1.2/1.3 仍需执行）

### 1.1 D-02：net10.0 LTS 单目标（已复核）

- .NET 10 是当前 **LTS**，支持至 **2028-11**。
- .NET 9（STS）已于 **2026-05** 结束支持；.NET 8 LTS 已于 **2026-11** 结束支持。
- 因此采用 **net10.0 单目标 + C# 14**，不再多目标。
- 影响：CI 矩阵从 2 TFM 降为 1 TFM；生成代码可用 C# 14；net8/net9 用户需升级。
- 结论：**无待办**，D-02 已最终确定。

### 1.2 D-06：名称检索

RunesHela 已作为项目名写入文档。发布前仍需：
1. NuGet 包名检索：`RunesHela`、`RunesHela.Cli`；
2. 商标检索（目标市场）；
3. 域名/社交账号可用性（文档中暂用 `runeshela.dev` 作为占位）；
4. GitHub 同名项目调研。
如冲突，备选：`Keel`、`Lintel`、`Clio`。

### 1.3 D-07：Apache-2.0 的合规动作

- 仓库根目录：`LICENSE` + `NOTICE`。
- NuGet：`PackageLicenseExpression=Apache-2.0`。
- 贡献：DCO（不用 CLA）。
- 发布物：保留版权/许可证/NOTICE；修改文件需声明。
- 第三方依赖（当前为零运行时依赖）需做许可证兼容审计。

## 2. 逐项决策记录

### D-01 产品路线：双引擎 + Agent 原生

**决定：C**

**背景**：纯性能会与 ConsoleAppFramework 正面竞争且差异化弱；纯优雅会与 CliFx/Spectre 同质化。两者交集（编译期模型）是空白区。

**考虑过的选项**：
- A 纯性能：范围小，但 star 天花板低，易被视为 CAF 影子。
- B 纯优雅：实现快，但缺硬指标与技术壁垒。
- C 双引擎 + Agent 原生：差异化最强，可分阶段。

**理由**：
1. 同一编译期模型可同时服务类优先与方法优先，边际成本可控。
2. Agent 契约是 2026 年新增空白，传播性强。
3. 产物同源（help/completion/schema/docs/MCP）构成长期护城河。

**影响**：架构必须围绕编译期模型；MVP 需严格控制范围。

**风险**：范围失控。缓解：V0.1 只做类优先 + 核心 + Agent 基础。

---

### D-02 目标框架：net10.0 单目标，C# 14

**决定：C**

**背景**：零开销依赖 `ISpanParsable<T>`、静态抽象与现代语言特性；net8/net9 均已结束支持，需要确定唯一目标。

**考虑过的选项**：
- A net8.0 起：覆盖面最大，但 net8 已结束支持。
- B net9.0 起：覆盖 net9/net10，但 net9 已结束支持且增加矩阵。
- C 仅 net10.0：唯一受支持 LTS，矩阵最小，可用 C# 14。

**理由**：按你的最终选择，net10.0 为唯一目标，C# 14；生成器仍为 `netstandard2.0`。

**影响**：
- 运行时与可选包：`net10.0`。
- CI 矩阵：1 TFM × 3 OS。
- 文档最低要求：.NET 10 SDK。
- 生成代码可用 C# 14；无需多目标条件编译。

**风险**：排除 net8/net9 用户。缓解：新项目定位 + 迁移指南；如未来确需存量，再评估多目标。

---

### D-03 包形态：极小运行时 + 生成器

**决定：B**

**背景**：纯 analyzer 可做到零程序集依赖，但类优先需要公共特性/入口/错误模型；MCP/Testing 需要共享运行时。

**考虑过的选项**：
- A 纯 analyzer：包体最小，但代码膨胀、修复困难。
- B 极小运行时 + 生成器：API 稳定、可组合、生成代码小。
- C 混合：兼顾但成本翻倍。

**理由**：单 NuGet 包内含运行时程序集 + `RunesHela.Generator` 分析器；依赖图仅 BCL。

**影响**：
- 包体预算 ≤ 60 KB/TFM。
- 生成器与运行时同版本锁定。
- “零依赖”口径为“零第三方运行时依赖”。

**风险**：用户误解“零依赖”。缓解：README 首屏明确口径。

---

### D-04 API 主轴：类优先 + 方法优先

**决定：C**

**背景**：类优先适合真实项目；方法优先是“一行 CLI”的传播点，但调用点生成复杂。

**考虑过的选项**：
- A 仅类优先：简单统一，但缺传播点。
- B 仅方法优先：极简，但复杂项目弱。
- C 两者分期：覆盖广、风险隔离。

**理由**：V0.1 类优先主 API；V0.2 以 `RunesHela.Script` 提供方法优先，独立入口避免与运行时类型冲突。

**影响**：
- 两套入口：`RunesHelaApp`（类优先）/`RunesHelaScript`（方法优先）。
- 方法优先不承诺复杂 DI/深层嵌套。
- 共享解析/绑定/快照测试。

**风险**：行为不一致。缓解：共享测试矩阵 + 明确适用边界。

---

### D-05 MVP 边界：标准 MVP

**决定：B**

**背景**：范围是最大风险；首发必须有足够卖点，但不能烂尾。

**考虑过的选项**：
- A 最小 MVP：快，但缺补全/Schema/配置，卖点不足。
- B 标准 MVP：类优先 + 嵌套 + ENV + 校验 + 过滤器 + DI + `describe` + `--yes` + 非 TTY 契约 + 模板。
- C 全量首发：功能完整，但周期长、质量风险高。

**理由**：标准 MVP 足以支撑“优雅 + Agent 原生”的叙事，并可在真实项目试用。

**影响**：V0.1 范围锁定；方法优先/补全/配置/Man/MCP 分期。

**风险**：范围仍偏大。缓解：按 03 任务 DAG 严格执行；P0 之外不插队。

---

### D-06 项目名称：RunesHela

**决定：RunesHela**

**背景**：名称影响 NuGet、仓库、域名、商标、搜索与社区记忆。

**考虑过的选项**：
- Truss（早期候选，已弃用）：结构支撑隐喻好，但需检索。
- Keel / Lintel / Clio / Armature：各有隐喻与冲突风险。
- RunesHela（你的选择）：独特、可检索、可品牌化。

**理由**：独特名称有利于搜索与商标；与“编译期/符文/结构”意象可建立品牌故事。

**影响**：
- 包：`RunesHela`、`RunesHela.Script`、`RunesHela.Mcp`、`RunesHela.Testing`、`RunesHela.Templates`、`RunesHela.Analyzers`。
- 命名空间：`RunesHela`。
- 入口：`RunesHelaApp`、`RunesHelaScript`。
- 诊断前缀：`RHL`（编译期 `RHL001`；运行时 `RHL_USAGE_*`）。
- 模板：`dotnet new runeshela-cli`。
- 文档域名占位：`runeshela.dev`。

**风险**：同名/商标冲突。缓解：§1.2 检索清单。

### D-07 许可证：Apache-2.0

**决定：B**

**背景**：MIT 最宽松但无显式专利授权；Apache-2.0 提供专利许可与报复条款，企业法务更熟悉。

**考虑过的选项**：
- A MIT：最短、采用门槛最低。
- B Apache-2.0：专利授权、企业友好。
- C 双许可：商业化灵活，但治理复杂。

**理由**：显式专利授权降低企业顾虑；仍属宽松许可；DCO 降低贡献门槛。

**影响**：LICENSE/NOTICE、包元数据、DCO、发布检查。

**风险**：NOTICE 遗漏/贡献者 IP。缓解：发布 checklist + DCO + 贡献指南。

---

### D-08 帮助来源：特性 > 文档注释 > 约定

**决定：C**

**背景**：文档注释自然；特性显式；约定零配置。需要明确优先级避免歧义。

**考虑过的选项**：
- A 注释优先：干净，但局部函数不支持。
- B 特性优先：稳定，但噪音大。
- C 双轨：灵活，需定义优先级。

**理由**：优先级为 **特性 > 文档注释 > 约定**；冲突给信息级诊断，不报错。

**影响**：生成器读取 `GetDocumentationCommentXml()`；缺失注释降级为 `RHL005` 信息。

**风险**：注释解析受编译配置影响。缓解：多 IDE/CI 测试 + 降级。

---

### D-09 输出渲染：自研极简 + 适配层

**决定：B**

**背景**：Spectre.Console 强在渲染，但依赖重、0.x、AOT 需注意；核心必须零第三方依赖。

**考虑过的选项**：
- A 依赖 Spectre：省事、漂亮，但违背零依赖。
- B 自研极简 + 适配层：轻、可控、可组合。
- C 纯文本：最轻，但体验弱。

**理由**：核心内置 text/markdown/json/table；`RunesHela.Rendering.Spectre` 为可选适配包。

**影响**：需实现 CJK 宽度、颜色能力、表格对齐；适配层跟随 Spectre 版本。

**风险**：自研不够美。缓解：极简风格 + 可选 Spectre。

---

### D-10 文档语言：英文优先，中文按需

**决定：B**

**背景**：OSS 国际采用需要英文；你作为评审者更习惯中文。

**考虑过的选项**：
- A 中文优先：评审快，但国际传播慢。
- B 英文优先：利于采用；中文按需提供。
- C 双语同步：覆盖广，但维护成本高。

**理由**：英文为主文档与 README；中文版作为可选翻译，不阻塞发布。

**影响**：文档写作以英文为主；中文版可后补；示例代码注释可中英按需。

**风险**：中文用户上手成本。缓解：保留中文 Quickstart（非必须）。

---

### D-11 MCP：Manifest + stdio server（分阶段）

**决定：C**

**背景**：MCP 生态增长快，但规范仍在演进；核心包不应绑定外部依赖。

**考虑过的选项**：
- A 不做：范围最小。
- B 只生成 Manifest：零依赖，但需外部宿主。
- C Manifest + stdio server：端到端可用。

**理由**：V1.x 先 `mcp --manifest`，稳定后提供 `RunesHela.Mcp` 可选包实现 stdio server。

**影响**：工具注解来自 `[Command]`；需要 JSON-RPC 生命周期/取消/错误映射。

**风险**：规范变化。缓解：适配层隔离 + 可选包。

---

### D-12 国际化：V1.x 可插拔资源

**决定：C**

**背景**：MVP 不需要框架消息国际化；但未来可能需要。

**考虑过的选项**：
- A 仅英文：最简单。
- B 中英内置：体验好，维护翻倍。
- C 可插拔资源：默认英文，用户可替换。

**理由**：MVP 只保证用户文案可自由使用中文；框架消息资源化放到 V1.x。

**影响**：需要设计资源接口；当前不做。

**风险**：后期改造成本。缓解：消息集中管理，不散落字符串。

---

### D-13 交互式提示：V1.x 独立包

**决定：B**

**背景**：交互提示与 AOT/非交互契约有冲突，核心不应内置。

**考虑过的选项**：
- A 不做：最稳，但缺向导体验。
- B 独立包：不污染核心。
- C 内置：开箱即用，但复杂度高。

**理由**：核心只定义 `IInput` 与 `--no-input` 语义；`RunesHela.Prompts` 后续提供。

**影响**：MVP 无提示；破坏性操作用 `--yes` 守卫。

**风险**：用户期望内置。缓解：文档明确分阶段。

---

### D-14 遥测与治理：零遥测 + 赞助

**决定：A**

**背景**：遥测会带来信任与合规成本；项目早期更需要信任。

**考虑过的选项**：
- A 零遥测 + 赞助：信任最高。
- B opt-in 遥测：数据驱动，但需披露。
- C 开放核心/商业版：收入，但社区分裂风险。

**理由**：默认不收集任何数据；通过 GitHub Sponsors/咨询/培训获得支持。

**影响**：无遥测代码；隐私政策简单；发布不包含网络上报。

**风险**：收入有限。缓解：优先赞助与咨询，不做功能阉割。
