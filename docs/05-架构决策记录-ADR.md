## ADR-001 包形态：极小运行时 + 生成器

**状态**：Accepted（2026-11-26；对应 D-03）

### 背景

ConsoleAppFramework 证明“纯 analyzer”可以做到零程序集依赖、零包体、AOT 增量极小。但 RunesHela 的类优先需要公共特性、入口类型、错误模型、测试控制台、可选 MCP；纯 analyzer 会导致生成代码膨胀、修复困难、可选能力无法共享。

### 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. 纯 analyzer | 零程序集；AOT 增量最小；叙事强 | 特性需生成；代码膨胀；修复难；高级能力弱 |
| B. 极小运行时 + 生成器 | API 稳定；可组合；生成代码小；可修复 | 多一个程序集；“零依赖”需解释 |
| C. 混合 | 兼顾 | 两套路径；成本翻倍 |

### 决策

采用 **B**：`RunesHela` 单个 NuGet 包（运行时程序集 + `RunesHela.Generator` 分析器程序集，仅 BCL 依赖）；方法优先另发纯 analyzer 包 `RunesHela.Script`。

### 理由

1. 类优先是主 API，需要稳定的公共类型。
2. 可选能力（Testing/MCP/Spectre 适配）应可组合，不应注入用户程序集。
3. 生成器缺陷可通过升级包修复，而不是要求用户重新生成。
4. 仍可宣称“零第三方运行时依赖”，这是企业最关心的部分。

### 影响

- 包体：运行时目标 ≤ 60 KB/TFM。
- 依赖：`RunesHela` 依赖图只有 BCL。
- 文档：明确“零第三方依赖 ≠ 零程序集”。
- 失败模式：生成器与运行时版本需匹配；包内锁定。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 用户误解“零依赖” | README 首屏明确口径 |
| 运行时膨胀 | 严格预算 + 裁剪 + 无 LINQ/反射 |
| 版本错配 | `RunesHela` 包内置同版本生成器；MSBuild 检查 |

### 相关

ADR-011（版本）、D-03。

## ADR-002 API 主轴：类优先 + 方法优先（分期）

**状态**：Accepted（2026-11-26；对应 D-04）

### 背景

类优先适合真实项目；方法优先适合微命令与传播。二者共享解析/绑定，但入口形态不同。方法优先需要在调用点生成解析器；由于 C# 不支持跨程序集 partial，若运行时库已定义 `RunesHela.Run`，生成器无法为其添加任意 lambda 重载。

### 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. 仅类优先 | 简单、统一 | 缺“一行 CLI”传播点 |
| B. 仅方法优先 | 极简、性能叙事强 | 复杂项目弱 |
| C. 两者分期 | 覆盖广、风险隔离 | 两套 API/文档 |

### 决策

采用 **C**：
- **V0.1**：类优先（主 API）。
- **V0.2**：`RunesHela.Script`（纯 analyzer）提供 `RunesHelaScript.Run(args, lambda)`，生成独立入口类型，避免与运行时 `RunesHelaApp` 冲突。

### 理由

1. 类优先是工程主流，先做可验证核心。
2. 方法优先技术风险高（调用点分析、增量缓存、重载解析），隔离到独立包。
3. 不承诺二者功能完全等价：脚本模式不支持复杂 DI/深层嵌套。

### 影响

- 文档需明确两套入口的适用场景。
- 生成器需支持两种发现模式，但共享模型/解析/绑定。
- API 命名：`RunesHelaApp`（类优先）/`RunesHelaScript`（方法优先）。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 两套行为不一致 | 共享快照测试矩阵 |
| 用户混淆入口 | 文档决策树 + 模板 |
| 方法优先生成器复杂 | 先支持简单类型/无 DI，逐步扩展 |

### 相关

ADR-001、ADR-013、D-04。

## ADR-003 帮助文本来源：特性 > 文档注释 > 约定

**状态**：Accepted（2026-11-26；对应 D-08）

### 背景

帮助文本的维护成本高、易漂移。文档注释自然；特性显式；约定零配置。

### 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. 文档注释优先 | 干净、同源 | 依赖注释解析；局部函数不支持 |
| B. 特性优先 | 稳定、明确 | 噪音大 |
| C. 双轨（特性覆盖） | 灵活 | 需定义优先级 |

### 决策

采用 **C**，优先级：**特性 > 文档注释 > 约定**。冲突时给 `RunesHela` 信息级诊断（不报错）。

### 理由

1. 默认零配置：命名约定 + 注释即可。
2. 需要精确控制时用特性覆盖（别名、短名、ENV、Secret、隐藏）。
3. 迁移友好：从其他框架迁移可先保留特性描述。

### 影响

- 生成器需读取 `ISymbol.GetDocumentationCommentXml()`。
- 需处理 `<summary>`/`<param>`/`<example>`/`<remarks>`。
- 文档注释缺失 → `RHL005` 信息。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 注释解析受编译配置影响 | 多 IDE/CI 测试；缺失时降级 |
| 特性与注释冲突 | 明确优先级 + 诊断 |
| 局部函数无注释 | 方法优先模式用特性/参数名 |

### 相关

ADR-002、D-08。

## ADR-004 语法策略：单遍、可预测、拒绝歧义

**状态**：Accepted（2026-11-26）

### 背景

POSIX/GNU 有大量历史语法（`-x` vs `-X`、短选项合并 `-fdx`、可选参数值、前缀匹配）。完整兼容会显著增加解析复杂度与冷启动开销。

### 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. 全兼容 POSIX/GNU | 用户熟悉 | 复杂、慢、歧义多 |
| B. 明确子集 | 快、可预测 | 少数习惯不支持 |
| C. 可配置语法 | 灵活 | 组合爆炸、文档难 |

### 决策

采用 **B**：
- 支持：`--long`、`--long=value`、`-s value`、`--` 终止符、重复选项、否定旗标、负数作为值、大小写不敏感（小写优先）。
- 不支持：短选项合并（`-abc`）、前缀缩写、`-x`/`-X` 区分、可选值歧义。
- 命令名大小写敏感。

### 理由

1. 冷启动场景下单遍解析收益最大。
2. 歧义语法是错误与安全问题的温床。
3. 明确规则比“尽量兼容”更容易文档化与测试。

### 影响

- 少量用户习惯需调整；提供迁移说明。
- 错误信息需明确“不支持合并短选项”。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 用户抱怨不兼容 | 明确文档 + `--` 透传兜底 |
| 与脚本习惯冲突 | 提供迁移指南与诊断提示 |

### 相关

02 §6.4、02 §8。

## ADR-005 配置：CLI > ENV > JSON > 默认

**状态**：Accepted（2026-11-26；对应 D-05）

### 背景

真实 CLI 需要多源配置；Microsoft.Extensions.Configuration 功能强但依赖多、绑定反射/分配重。需要一套零反射、可预测、可脱敏的方案。

### 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. 仅 CLI | 最简单 | 不符合工程习惯 |
| B. CLI + ENV | 轻量 | 缺文件配置 |
| C. CLI + ENV + JSON | 完整、可控 | 需实现优先级/校验/Schema |
| D. 集成 MEDI Configuration | 生态兼容 | 重依赖、反射、AOT 风险 |

### 决策

采用 **C**，V1.0 实现：
- 优先级：CLI > ENV > 文件 > 默认。
- 文件格式：JSON（`JsonDocument`，无反射、AOT 安全）。
- 键路径：`section.key`；`[Option(Config = "deploy.environment")]`。
- 生成配置 Schema；非法配置 → 退出码 3。

### 理由

1. JSON 是 .NET 生态默认，BCL 自带、AOT 安全。
2. 零反射绑定符合项目定位。
3. 显式优先级避免“配置地狱”。
4. 不引入 MEDI 依赖；需要时用户可自行桥接。

### 影响

- 配置键成为公共契约（需版本化）。
- 脱敏规则需覆盖文件/ENV/CLI。
- Schema 生成增加产物。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 用户想要 YAML/TOML | V1.x 通过 `IConfigSource` 扩展 |
| 与 MEDI 配置重复 | 提供桥接示例，不内置 |
| 优先级误解 | 帮助中显示来源 + `--verbose` |

### 相关

02 §9、D-05。

## ADR-006 DI：生成构造注入，不内置容器

**状态**：Accepted（2026-11-26）

### 背景

类优先需要构造注入；内置容器会重造 MEDI、增加 AOT 风险；反射激活会破坏零反射。

### 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. 不提供 DI | 最简单 | 复杂项目不适 |
| B. 生成构造注入 + 用户 `IServiceProvider` | 零反射、AOT 友好、可组合 | 需用户注册服务 |
| C. 内置容器 | 开箱即用 | 范围爆炸、AOT 风险 |

### 决策

采用 **B**：
- 生成代码直接 `new Command(services.GetService(typeof(ILogger))...)`。
- 无 provider 时仅支持无参构造；否则明确错误。
- 不扫描程序集、不做属性注入。

### 理由

1. 构造函数是显式依赖，便于测试。
2. `IServiceProvider` 是 BCL 抽象，MEDI/自制容器均可。
3. 避免反射激活与生命周期魔法。

### 影响

- 用户需理解“命令由生成器激活”。
- 服务解析失败 → 明确错误（含缺失类型）。
- AOT 下推荐显式工厂注册。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 用户期望自动扫描 | 文档明确“显式注册” |
| 开放泛型服务 AOT 问题 | 诊断 + 文档建议 |

### 相关

02 §13.2、D-04。

## ADR-007 渲染：核心零依赖，适配层可选

**状态**：Accepted（2026-11-26；对应 D-09）

### 背景

Spectre.Console 是 .NET 富终端事实标准，但依赖重、0.x、AOT 需注意；核心若绑定它会违背“零第三方依赖”。

### 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. 内置 Spectre | 漂亮、省事 | 重依赖、AOT 风险 |
| B. 自研极简 + 适配层 | 轻、可控、可组合 | 需维护基础渲染 |
| C. 仅纯文本 | 最轻 | 体验弱 |

### 决策

采用 **B**：
- 核心内置 text/markdown/json/table（极简）。
- `RunesHela.Rendering.Spectre` 可选包适配 `IResult`。
- 帮助渲染保持自研（宽度/CJK/无框线）。

### 理由

1. 核心必须零第三方依赖。
2. 大多数 CLI 只需表格/列表/JSON，不需要完整 TUI。
3. 需要美感时可组合 Spectre，不绑架用户。

### 影响

- 需实现 CJK 宽度、颜色能力、表格对齐。
- 适配层需跟随 Spectre 版本。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 自研渲染不够美 | 极简风格 + 可选 Spectre |
| 表格边界 | 快照测试 + 80/120 列 |

### 相关

ADR-001、D-09。

## ADR-008 Agent 契约：默认开启、可覆盖

**状态**：Accepted（2026-11-26；对应 D-05）

### 背景

Agent 已成为 CLI 的重要消费者；现有框架默认输出人类文本，Agent 需反复试错。需要一套默认行为，同时不干扰人类用户。

### 决策

采用以下契约：
1. **TTY 检测**：非 TTY 去色、去 spinner、去交互；数据走 stdout，诊断走 stderr。
2. **结构化错误**：`code`/`message`/`hint`/`nextSteps[]`/`docsUrl`/`exitCode`。
3. **退出码固定**：0/1/2/3/4/5/6/7/130。
4. **破坏性守卫**：非 TTY 且无 `--yes` → 立即失败（退出码 2），不挂起。
5. **自描述**：`describe`/`schema`/`--help --json`。
6. **显式覆盖**：`--format`/`--plain`/`--json` 可覆盖自动行为。

### 理由

1. 默认正确 > 让用户配置。
2. 契约稳定才能被脚本/Agent 依赖。
3. 人类体验不受损：TTY 下仍是友好文本/颜色。

### 影响

- 输出格式成为公共 API（需版本化）。
- 所有命令默认继承全局选项。
- 测试需覆盖 TTY/非 TTY 两种环境。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 破坏现有脚本 | 显式 `--format text` 可恢复 |
| Agent 误判 | `describe` 提供权威模型 |
| 退出码争议 | 文档化 + 可自定义 `RunesHelaError.ExitCode` |

### 相关

02 §10、D-05。

## ADR-009 MCP：可选包、同源生成、分阶段

**状态**：Accepted（2026-11-26；对应 D-11）

### 背景

MCP 生态增长快，但规范仍在演进；核心包不应绑定外部依赖。

### 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. 不做 | 范围小 | 错过生态 |
| B. 只生成 Manifest | 零依赖 | 需外部宿主 |
| C. Manifest + stdio server | 端到端 | 依赖/规范风险 |

### 决策

采用 **C**，但分阶段：
- V1.x 先 `mcp --manifest`（从同一模型生成工具清单）。
- 稳定后提供 `RunesHela.Mcp` 可选包实现 stdio server。
- 核心包不引入 MCP 依赖。

### 理由

1. 同源生成保证 CLI 与 MCP 工具一致。
2. 可选包隔离规范变化风险。
3. Manifest 已能满足多数宿主集成。

### 影响

- 工具注解（只读/破坏性/幂等）来自 `[Command]`。
- 需要 JSON-RPC 生命周期/取消/错误映射。
- 测试需覆盖工具 schema 一致性。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| MCP 规范变化 | 适配层 + 版本化 |
| 工具与 CLI 行为不一致 | 同一执行管线 |
| 安全（Agent 自动调用） | 破坏性守卫 + dry-run |

### 相关

02 §11.5、D-11。

## ADR-010 目标框架：net10.0 单目标，C# 14

**状态**：Accepted（2026-11-26；对应 D-02=C）

### 背景

零开销依赖 `ISpanParsable<T>`、静态抽象与现代语言特性。net8/net9 均已结束支持，继续多目标只会增加构建/测试成本；net10 是当前 LTS（支持至 2028-11）。

### 决策

- 运行时：`net10.0` 单目标。
- 生成器：`netstandard2.0`。
- 语言：C# 14。
- 不支持 .NET Framework / netstandard2.0 运行时 / Unity。

### 理由

1. 遵守 D-02=C：只用受支持的 LTS，避免 EOL 运行时。
2. 现代 API 与 C# 14 足以实现零开销与最佳体验。
3. 最小 CI 矩阵（1 TFM），减少条件编译与发布组合。
4. 放弃旧平台换取架构简单与性能。

### 影响

- CI 矩阵 1 TFM × 3 OS。
- 无需多目标条件编译，生成代码可用 C# 14。
- 文档最低要求：.NET 10 SDK。
- net8/net9 用户需升级或停留在旧版本。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 排除 net9/net8 存量用户 | 新项目定位；提供迁移指南；必要时再评估多目标 |
| 用户 SDK 未升级 | 明确最低要求 + 安装检查 + 文档指引 |
| C# 14 特性兼容性 | 生成代码保持可读；仅使用稳定特性 |

### 相关

02 §4.2、D-02。

## ADR-011 版本与包：SemVer、同版本锁定、ApiCompat

**状态**：Accepted（2026-11-26）

### 背景

生成器与运行时强耦合；公共 API 与生成代码需要不同的兼容策略。

### 决策

- 包版本：SemVer 2.0；`RunesHela` 与 `RunesHela.Generator` 同版本发布并锁定。
- 公共 API：特性、运行时类型、MSBuild 属性、JSON Schema 字段、帮助中的稳定字段。
- 非公共：生成代码命名/布局、内部类型、常量。
- 弃用：`[Obsolete]` + 诊断 + 至少 2 个 minor 版本。
- 门禁：ApiCompat、生成快照、Schema 兼容、行为兼容。

### 理由

1. 用户依赖的是“行为 + 公共 API”，不是生成代码。
2. 同版本锁定避免“生成器/运行时错配”。
3. 兼容门禁把破坏性变更挡在 CI。

### 影响

- 发布流程需基线包与兼容报告。
- 大版本允许破坏，但需迁移指南。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 生成代码被用户直接引用 | 文档禁止；命名空间隔离 |
| 兼容门禁误报 | 白名单 + 评审 |

### 相关

ADR-001、02 §17。

## ADR-012 性能：预算化、可复现、CI 门禁

**状态**：Accepted（2026-11-26）

### 背景

“极致性能”若不可复现，就是营销。需要把性能变成工程约束。

### 决策

1. 微基准（BenchmarkDotNet）+ 冷启动（hyperfine）+ 体积（publish diff）+ 生成器（驱动基准）。
2. 预算写入 PRD/技术设计；PR 超阈值失败。
3. 每次发布保存基线 JSON 与硬件信息。
4. 公开基准报告，允许第三方复现。
5. 热路径禁止 LINQ/正则/`Split`/装箱/异常。

### 理由

1. 没有门禁的性能会悄悄退化。
2. 可复现性建立信任。
3. 预算让取舍可讨论（例如“这个特性值 200B 吗”）。

### 影响

- CI 需要固定 runner/容差。
- 特性开发需评估预算。
- 发布流程增加基准步骤。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| CI 噪声导致误报 | 多次采样 + 容差 + 专用 runner |
| 预算阻碍功能 | 预算分级（核心/可选） |

### 相关

02 §12、04 清单。

## ADR-013 生成器：增量、调用点分析、失败降级

**状态**：Accepted（2026-11-26）

### 背景

生成器是性能与体验的核心，也是最容易拖垮 IDE 的部分。方法优先需要调用点分析；类优先需要符号建模。

### 决策

- 使用 `IIncrementalGenerator` + `ForAttributeWithMetadataName`。
- 模型为不可变 record + `EquatableArray`；不捕获 `Compilation`/`ISymbol`。
- 方法优先用 `CreateSyntaxProvider` 匹配调用点，分析 lambda 参数。
- 每个命令生成独立文件；路由/入口单独生成。
- 内部异常捕获为 `RHL999`，生成兜底入口，不炸构建。
- 生成器自带性能基准与快照测试。

### 理由

1. 增量缓存决定 IDE 体验。
2. 独立文件便于定位与 diff。
3. 失败降级避免“编译器插件一崩，项目全废”。

### 影响

- 生成器代码需严格的相等性设计。
- 快照测试覆盖所有产物。
- 生成代码可读性成为验收项。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 缓存失效导致全量重跑 | 相等性测试 + 基准 |
| 调用点分析边界多 | 先支持简单 lambda，诊断不支持形态 |
| 生成代码膨胀 | 按需生成模块（帮助/产物分开） |

### 相关

ADR-002、02 §6。

## ADR-014 错误模型：结构化、稳定、可渲染

**状态**：Accepted（2026-11-26）

### 背景

错误是 CLI 最常被脚本/Agent 消费的部分；字符串错误无法稳定解析。

### 决策

- 统一 `RunesHelaError`：`code`/`message`/`hint`/`nextSteps`/`docsUrl`/`exitCode`/`commandPath`/`details`。
- 错误码命名：`RHL_<类别>_<原因>`（如 `RHL_USAGE_UNKNOWN_OPTION`）。
- 正常路径不抛异常；错误用返回值。
- 人类/Markdown/JSON 三种渲染，同一数据源。
- 未知异常 → 退出码 1；堆栈仅 `--verbose`/`RHL_DEBUG=1`。

### 理由

1. 结构化错误是 Agent 自愈的前提。
2. 稳定错误码可被脚本依赖。
3. 避免异常控制流带来的性能与噪声。

### 影响

- 错误码成为公共 API。
- 所有内置错误需文档页。
- 用户自定义错误需遵循模型。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 错误码膨胀 | 分类 + 审查 |
| nextSteps 质量参差 | 模板 + 评审 |

### 相关

02 §7.6、ADR-008。

## ADR-015 补全：静态脚本 + 隐藏动态协议

**状态**：Accepted（2026-11-26）

### 背景

补全是 CLI 体验的重要部分；动态补全需要 shell 与进程协作；不能污染帮助与 Agent 契约。

### 决策

- `completion <shell>` 输出静态脚本（命令/选项）。
- 隐藏命令 `__complete` 提供动态候选（文件/上下文）。
- 四 shell：bash/zsh/fish/pwsh；CI 冒烟。
- 不在 `--help` 中暴露 `__complete`；不写入文档主流程。

### 理由

1. 静态脚本覆盖 90% 场景，零运行时成本。
2. 动态协议隔离复杂性与安全风险。
3. 四 shell 覆盖主流环境。

### 影响

- 补全脚本需转义与快照。
- 动态补全需处理超时/错误（静默失败）。
- 与 Agent 契约隔离。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| shell 差异 | 四 shell 集成测试 |
| 动态补全注入 | 严格转义 + 不执行输入 |
| 维护成本 | 生成而非手写 |

### 相关

02 §11.3、D-05。

## ADR-016 许可证：Apache-2.0

**状态**：Accepted（2026-11-26；对应 D-07=B）

### 背景

许可证影响企业采用、贡献意愿与专利风险。MIT 最宽松但缺少显式专利授权；Apache-2.0 在保持宽松的同时提供专利许可与专利报复条款，企业法务更熟悉。

### 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. MIT | 最短、最宽松 | 无显式专利授权 |
| B. Apache-2.0 | 专利授权；企业友好；仍宽松 | 文本更长；需 NOTICE |
| C. 双许可 | 开源 + 商业 | 治理复杂；社区敏感 |

### 决策

采用 **B：Apache-2.0**。

具体要求：
- 仓库根目录包含 `LICENSE` 与 `NOTICE`。
- NuGet 包元数据声明 `PackageLicenseExpression=Apache-2.0`。
- 源文件不强制加 SPDX 头，但发布物必须包含许可证与 NOTICE。
- 贡献采用 **DCO**（Developer Certificate of Origin），不要求 CLA。
- 修改/再分发需保留版权、许可证与 NOTICE 声明。

### 理由

1. 显式专利授权降低企业采用顾虑。
2. 与 .NET OSS 生态主流许可证兼容。
3. 仍属宽松许可，不阻碍商业使用与再分发。
4. DCO 降低贡献门槛，避免 CLA 摩擦。

### 影响

- 发布清单增加 LICENSE/NOTICE 检查。
- 第三方依赖（当前为零运行时依赖）需做许可证兼容审计。
- 文档与包元数据需统一声明 Apache-2.0。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| NOTICE 遗漏 | 发布 checklist + 自动化检查 |
| 贡献者雇主 IP 争议 | DCO 签署 + 贡献指南说明 |
| 与 GPL 项目组合使用 | 文档说明兼容性边界，不提供法律意见 |

### 相关

D-07、04 §11 发布清单。
