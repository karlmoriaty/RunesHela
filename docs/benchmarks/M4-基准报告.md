## 2. 非 TTY 与输出模式（T-036）

- 帮助恒为常量文本，不含 ANSI；错误仅在 `IConsole.IsAnsiSupported` 为真时着色（`NO_COLOR`/`TERM=dumb`/非 TTY 自动关闭）。
- 全局选项可在命令前解析：`--json`、`--plain`、`--no-color`、`--quiet`、`--verbose`、`--no-input`、`--yes`、`--format <text|plain|json>`；未知格式 → 退出码 2。
- `--json` 或 `--format json` 使帮助与错误使用 JSON；数据始终写 stdout，诊断写 stderr。
- `describe` 忽略输出模式，始终输出 JSON（供 Agent 消费）。

**与设计的偏差**：非 TTY 默认格式按设计应为 Markdown；本轮默认纯文本（`--plain` 语义），Markdown 渲染随 M5 文档产物（T-045）一起实现，避免两套渲染漂移。

## 3. 结构化错误（T-037）

- 所有错误对象包含 `code`、`message`、`hint`、`nextSteps`、`docsUrl`、`command`、`exitCode`。
- did-you-mean：未知命令/选项时按编辑距离（≤2，前缀匹配优先）给出候选；候选集在生成期确定，运行时只读数组。
  距离计算使用 `stackalloc`，错误路径堆分配保持 304 B。
- 新增错误码：`RHL_USAGE_CONFIRMATION_REQUIRED`、`RHL_USAGE_ABORTED`、`RHL_USAGE_UNSUPPORTED_FORMAT`、`RHL_INTERNAL_UNEXPECTED`。
- 未处理异常在顶层捕获：消息 + `--verbose` 时的完整异常文本；退出码 1，不打印堆栈到 stdout。

## 4. 破坏性守卫（T-038 / AC-08）

行为矩阵（与设计 §10.5 一致）：

| 环境 | `--yes` | 行为 |
|---|---|---|
| 非 TTY / `--no-input` | 否 | **立即失败**：退出码 2，`nextSteps` 提示 `--yes`，不等待输入 |
| TTY | 否 | stderr 提示 `Continue? [y/N]`；`y/yes` 执行，否则退出码 2 |
| 任意 | 是 | 直接执行 |

帮助与 JSON 模型会为破坏性命令追加 `-y, --yes` 与 `--no-input` 选项。集成测试覆盖非 TTY、拒绝、确认、`--no-input` 四种路径。

## 5. 退出码与 EPIPE（T-040 / T-041）

| 码 | 常量 | 场景 |
|---:|---|---|
| 0 | `Success` | 成功 |
| 1 | `Failure` | 一般失败 / 未处理异常 |
| 2 | `Usage` | 用法错误、校验失败、未确认 |
| 3~7 | `Configuration` / `NotFound` / `Permission` / `Conflict` / `Timeout` | 业务语义 |
| 130 | `Interrupted` | `CancellationToken` 取消 |
| 141 | `BrokenPipe` | 顶层 `IOException`（管道关闭） |

`RunesHelaApp` 在顶层统一映射；141 不写错误信息（诊断通道可能同样关闭）。集成测试用抛 `IOException` 的 `TextWriter` 验证 141。

## 7. 过滤器链（T-034）

```csharp
[Command("purge", IsDestructive = true, Filters = new[] { nameof(AuditFilter), nameof(TimingFilter) })]
```

- 生成静态链：`filter0.InvokeAsync(context, ctx1 => filter1.InvokeAsync(ctx1, ctx2 => RunHandler(command)))`。
- `CommandContext` 提供命令路径、服务提供器、取消令牌；过滤器按声明顺序进出。
- 生成期校验：名称必须唯一解析到可实例化类、实现 `IRunesHelaFilter`、有 public/internal 无参构造（RHL037/038/039）。
- 使用 `nameof(...)` 字符串而不是 `typeof(...)`：避免 `System.Type` 元数据把 Native AOT 反射栈（约 150 KB）带入产物。
- 分配：每个过滤器 1 个实例 + 闭包；仅在配置过滤器时产生，未配置路径保持零额外分配。

集成测试验证顺序：`outer:before → inner:before → handler → inner:after → outer:after`，退出码由 handler 透传（5）。

## 8. 性能

本地 ShortRun（Windows 11 / .NET 10.0.15）：

| 方法 | M3 | M4 | Allocated | 预算（失败阈值） |
|---|---:|---:|---:|---|
| Help | 12.62 ns | 20.69 ns | 0 B | ≤ 5.5 µs / ≤ 128 B |
| Route | 14.22 ns | 31.46 ns | 24 B | ≤ 1.1 µs / 0 B（不含实例） |
| Error | 58.20 ns | 1,550 ns | 304 B | ≤ 5.5 µs / ≤ 1 KB |
| FiveOptions | 201.82 ns | 208.14 ns | 56 B | ≤ 1.1 µs / 0 B（不含实例） |

解读：

- 根路由新增全局选项扫描与叶子帮助扫描，路由/帮助耗时上升约 15~20 ns，仍低于预算两个数量级。
- 错误耗时上升来自 did-you-mean 的候选距离计算；分配保持 304 B（`stackalloc`，无新增堆分配），远低于 1 KB 阈值。
- 绑定路径不变（208 ns / 56 B = 命令实例）；同步入口新增 `IsCompletedSuccessfully` 快路径，避免异步状态机开销。

**门禁分层**：

- 分配断言在 `tests/RunesHela.Performance.Tests`（Release）中精确执行，CI 直接失败。
- 延迟断言在共享 runner 上仅作烟测上限（绑定 10 µs、帮助/错误 20 µs），避免 CPU 抢占导致抖动。
- 绝对延迟预算（1.1 µs / 5.5 µs）由 `perf` job 的 BDN 结果执行：脚本解析 `Statistics.Mean`，超出即失败。
  首次 M4 CI 中 xUnit 实测 1134.8 ns（阈值 1100 ns）触发失败，说明共享 runner 的纳秒级断言不可靠，故改为 BDN 均值门禁 + xUnit 分配门禁。

## 9. AOT 与发布

CI 矩阵沿用 M3：linux-x64 / win-x64 / osx-arm64 AOT + Trim/SingleFile + R2R，全部通过。

| 指标 | M3 | M4 | 预算 | 结论 |
|---|---:|---:|---:|---|
| 启动增量 p50 | 0.14 ms | **-0.06 ms** | ≤ 1 ms | ✅ |
| 体积增量 | 128,856 B | **286,264 B（279.6 KB）** | 目标 ≤ 100 KB；失败阈值 > 150 KB | ❌ 超阈值 |

体积分析：

- 体积增量与 M4 功能集合相关，但在移除异步入口包装、拆分交互式输入、把过滤器改为 `nameof` 字符串注册后**未发生变化**，说明增量来自新增代码/元数据的组合而非单点。
- 已确认 Native AOT map 中出现 `System.Console.TerminalFormatStrings`、`Reflection.Execution.NativeFormatEnumInfo` 等节点，后续需用 map 逐项裁剪。
- M8 发布前必须收敛到 ≤ 100 KB；候选手段：按需剥离 `describe`/帮助 JSON、拆分错误渲染器、用链接描述文件裁剪未用 Console 能力、复核 `CommandAttribute` 元数据。
- AC-13（构建成功、0 警告、产物可运行）仍通过；体积预算不达标属于已知技术债。
